# Reduced Motion and the Preference System

## Key Facts
- macOS "Reduce motion" is ON on the primary dev machine used for this project — verified via `defaults read com.apple.universalaccess reduceMotion`, which returns `1`. Any CSS gated on `prefers-reduced-motion: reduce` will match and take effect on this machine by default.
- CSS cannot conditionally "un-match" a media query — once `prefers-reduced-motion: reduce` matches, there is no pure-CSS way to selectively ignore it for one feature while still respecting it elsewhere in the same stylesheet.
- The gomuks preference system pattern: new preferences are declared in `web/src/preferences.ts` with an `allowedContexts` value (`globalDeviceSpecific` for a per-device setting); anything that needs to drive CSS (rather than just app logic) is wired through `StylePreferences.tsx`, which is the place that translates a preference value into a DOM attribute or class other stylesheets can select on.

## Gotchas
- If every `prefers-reduced-motion: reduce` rule in the app is written as `animation: none` / `transition: none`, then on a machine with Reduce Motion enabled, EVERY animation in the app is permanently disabled — including ones added later that were never tested with Reduce Motion off, because the developer may not realize their own OS setting is silently suppressing what they just wrote. Always check the actual `prefers-reduced-motion` matchMedia state directly when an animation "doesn't seem to run," rather than assuming the code is broken.
- Reduce Motion should not mean "remove all feedback" — replacing an animation with `none` under `prefers-reduced-motion` is not the only valid choice. A 120ms opacity fade (or similarly minimal, non-motion cue) satisfies the accessibility intent while still giving the user *some* signal that state changed.
- A CSS-only escape hatch is not enough if any JS also reads `matchMedia('(prefers-reduced-motion: reduce)')` directly to make a layout decision (e.g. `MainScreen.tsx`'s `activeRoomReducer`, which uses it to decide whether to keep an outgoing room mounted during a transition). The JS check needs the same escape-hatch condition applied, or toggling the preference only half-fixes the behavior — the CSS animates but the JS still behaves as if motion is off (or vice versa).

## Patterns That Work
- To let a preference override a media query, don't try to fight the media query in the rule that already has it — add a SEPARATE attribute-based condition to the selector that the preference toggles, and require that attribute's ABSENCE alongside the existing `prefers-reduced-motion: reduce` match. Concretely: `StylePreferences.tsx` sets `data-ignore-reduce-motion` on `<html>` via a `useEffect` bound to the preference value; every affected rule becomes `html:not([data-ignore-reduce-motion]) .thing { ... reduced motion styles ... }` (exact selector shape may vary by file, but the requirement is the same: the reduced-motion styles apply only when the override attribute is absent).
- When adding a new animation to this app, proactively check whether a reduced-motion rule already exists for the element/area and whether it needs the same `data-ignore-reduce-motion` escape hatch wired in, rather than assuming reduced-motion handling is optional or can be added later.
- **Exit-animation state machines:** when an animation state machine (e.g., a drawer closing) relies on the `animationend` event listener to trigger a cleanup step, **JS must also check reduce-motion state and skip the exit state entirely for reduce-motion users.** Under `prefers-reduced-motion: reduce` + `animation: none`, the `animationend` event never fires, so cleanup doesn't happen and the transition is half-applied (element is visually in the final state but DOM is still in the old state). Fix: check `window.matchMedia('(prefers-reduced-motion: reduce)').matches` in the state machine and jump directly to the cleanup state, skipping the `animation: none` state that would leave the event listener hanging.
- **Grid collapse animation:** use `grid-template-rows: 0fr ↔ 1fr` with `transition: grid-template-rows <duration>` for smooth height collapse/expand. **Critical:** the inner flex/block container must have `min-height: 0` (grid's auto-minimum otherwise refuses to collapse to 0fr). Inner padding must be on a child element, not the flex container itself, or padding takes space during collapse. Example: grid cell contains a flex container with `min-height: 0` (the collapse-capable element) which itself contains a `<div>` with `padding: ...` (holds the actual content). **Reduce-motion gate:** in CSS, the transition applies only when reduce-motion is not enabled AND the override attribute is absent: `html:not([data-ignore-reduce-motion]) grid-item { transition: grid-template-rows .26s ... }`. In JS, state changes to the opening state happen immediately; closing state is skipped for reduce-motion users (jump to closed state instead, which has `grid-template-rows: 0fr` with no transition).
